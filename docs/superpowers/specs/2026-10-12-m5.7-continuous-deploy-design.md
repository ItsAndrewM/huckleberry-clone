# M5.7: deploy every green push to main — design

**Date:** 12 October 2026. **Status:** approved by Andrew on 12 October 2026. It was then revised after the final review: D14 changed how a deploy runs. Andrew made each decision below on 12 October 2026, D1 to D13 in a grill of the options and D14 when the review's finding came in.

## Goal

Every push to `main` deploys to production at https://baby.andamonium.dev once CI's gates, `check` and `e2e`, pass on that commit. Nobody has to run anything. `pnpm release` stays as a manual fallback that runs the same deploy script.

## Today

- **Deploys are manual.** `pnpm release` runs in the main checkout when Andrew says so. It refuses unless the checkout is a clean `main` at `origin/main` with green CI. Then it builds without `CLOUDFLARE_ENV` and checks the built config. It also saves the household's JSON export to `exports/` and takes a PITR bookmark through the admin token. Finally it runs `wrangler deploy` and appends the time, the commit and the bookmark to `deploys.log`.
- **CI** (`.github/workflows/ci.yml`) runs `check` and `e2e` on every pull request and every push to `main`, and deploys nothing. A newer push to the same ref cancels a run in progress.
- **Constraints that shape the design:**
  - The repo is private, on GitHub Free. GitHub environments (environment secrets, required reviewers, deployment branch rules) and branch protection aren't available, so any secret is a repo-wide Actions secret.
  - The admin service token and the exports live only on Andrew's Mac. An export holds every row, the child's name and birth date included.
  - Durable Objects point-in-time recovery keeps 30 days. `pnpm admin pitr:restore --at <time>` already rewinds to any moment in that window, the same window a bookmark has. Cloudflare offers no way to take or restore a bookmark from outside the Worker.

## Decisions

| # | Question | Decision | Why, and what was turned down |
|---|---|---|---|
| 1 | Which deploy path | A GitHub Actions workflow that runs the repo's pinned Wrangler | Cloudflare's CI/CD page offers Workers Builds and external CI without preferring either in general. Workers Builds deploys every push to its production branch and can't wait for GitHub's checks. Its workarounds were turned down: upload-only builds still need a token in GitHub, and they can't change Durable Object classes or the Custom Domain; moving the gates into Cloudflare's build image duplicates CI under a 20-minute limit. The `cf` CLI is in beta. Cloudflare's newer docs call Wrangler directly rather than through `wrangler-action` |
| 2 | What starts a deploy | A separate `deploy.yml`, started when the CI workflow completes | CI keeps cancelling older runs, and that can never cut a deploy off halfway. `pnpm release`'s CI check reads a run that holds only the gates. Turned down: a `deploy` job inside `ci.yml`, which would have to stop cancelling runs on `main` and would see its own run still in progress |
| 3 | What protects data before a deploy | The deploy records a restore point, the UTC second just before the new version goes live | No household credential or data goes to GitHub. Turned down: a deploy-only bookmark token (Worker and Access changes), the admin token in GitHub with exports as workflow artifacts, and exports written to R2 by the Worker |
| 4 | `main` moved on before the deploy starts | Skip, with a notice, and end green | Only main's head deploys, as `pnpm release` works today. A re-run of an old commit's CI can never roll production back. Turned down: deploying any green commit newer than the live one (needs a lookup in Cloudflare's history), and failing red |
| 5 | Pausing deploys | `gh workflow disable deploy.yml`, then `gh workflow enable deploy.yml` | GitHub's own switch, so nothing to build. Turned down: a `DEPLOYS_PAUSED` repo variable, and no switch at all |
| 6 | The record of each deploy | Cloudflare's deployment history: each version is tagged with its commit, and each deployment's message holds the restore point. The run summary repeats it. `deploys.log` is retired | One list holds the deploys, from CI or from `pnpm release`. Cloudflare's list shows the last 10, and older restore points stay in the Deploy runs on GitHub for 90 days. Turned down: keeping `deploys.log` for manual runs only, and a git tag per deploy |
| 7 | The Cloudflare token | An API token with the Workers Editor role on the `baby-tracker` Worker only, with no expiry | Cloudflare says Editor on one Worker deploys new versions of it, as long as the deploy doesn't add, change or remove its Custom Domain. D14's upload-then-deploy never touches the domain. No expiry matches the admin token. Turned down: the zone permission, and the "Edit Cloudflare Workers" template |
| 8 | `pnpm release` | Kept as a local fallback that runs the same script | It covers a failed or paused CI deploy. Turned down: retiring it |
| 9 | What the fallback needs | Green CI on the commit, as today | During a full GitHub Actions outage, roll back with `wrangler rollback` and wait. Turned down: running the gates on the Mac |
| 10 | Docs-only pushes | They deploy like any other | 2 of the 31 merges to `main` so far changed only docs. A path filter isn't worth its edge cases |
| 11 | Exports | By hand only, with `pnpm admin export` | No scheduled export and no follow-up item. Andrew exports when he wants a copy older than PITR's 30 days, or one to test a migration on |
| 12 | Failure alerts | GitHub's failure email | GitHub's Actions notifications already email the person a failed run is attributed to, and for a deploy that should be whoever merged (see Risks). A skipped or superseded deploy ends green, so it stays quiet. Turned down: ntfy pushes on failure or on every deploy |
| 13 | The iPhone device checklist | Run after a deploy whose change needs it | A PR that changes sign-in or Access, the service worker, the manifest or install flow, or iOS-specific behaviour says "device checklist after deploy" in its body. Other deploys skip it. Turned down: weekly, and after every deploy |
| 14 | How the deploy runs (decided after the final review) | `wrangler versions upload`, tagged with the commit, then `wrangler versions deploy <version-id>@100%` | The final review found, and Wrangler 4.148.0's code confirms, that `wrangler deploy` puts the new version live before it re-sends the Custom Domain, which it does on every non-interactive run. Cloudflare says Custom Domains don't support per-Worker roles, so with D7's token every CI deploy would most likely go live and then fail red. Uploading, then deploying, never touches the domain, and a failure at either step leaves the previous version live. The version ID comes from Wrangler's output file, because `--version-tag` refuses a tag that two uploads share, as a re-run would make. The cost: a commit that adds, renames or deletes a Durable Object class can't be uploaded as a version, so it deploys by hand with `wrangler deploy`. Turned down: a token for every Worker plus the zone's routes, and keeping `wrangler deploy` to see what the first deploy does |

## How a deploy runs

### `.github/workflows/deploy.yml`

- **Trigger:** `workflow_run` for the workflow named `CI`, type `completed`, branch `main`.
- **Condition:** the job runs only if that run's `conclusion` is `success` and its `event` is `push`.
- **One at a time:** `concurrency` group `deploy-production` with `cancel-in-progress: false`. A running deploy is never cancelled, and a newer waiting deploy replaces an older waiting one.
- **Permissions:** `contents: read` and `actions: read`.
- **Time limit:** the job stops after 20 minutes, so a hung step can't hold up the deploys waiting behind it.
- **Actions:** GitHub's own actions by tag, as in `ci.yml`. The one third-party action, `pnpm/action-setup`, is pinned to a commit, because this job holds the token.
- **Steps:**
  1. Check out `github.event.workflow_run.head_sha`, the commit CI tested. A `workflow_run` job's own `github.sha` is main's latest commit, which CI may not have tested.
  2. Set up pnpm and Node from `.nvmrc`, then run `pnpm install --frozen-lockfile`. Neither step gets a token.
  3. Compare the checked-out commit with `git ls-remote origin refs/heads/main`. If they differ, write a notice, "main moved on to `<sha7>`, which deploys after its own CI", and skip the last step. The job ends green. This check comes after the install, so only a second or so passes before the release's own fetch.
  4. Run `pnpm release`, with `CLOUDFLARE_API_TOKEN` from the repo secret and `GH_TOKEN` set to the job's own token.

This sketch shows the shape. The plan holds the exact file.

```yaml
name: Deploy

on:
  workflow_run:
    workflows: [CI]
    types: [completed]
    branches: [main]

permissions:
  contents: read
  actions: read

concurrency:
  group: deploy-production
  cancel-in-progress: false

jobs:
  deploy:
    if: github.event.workflow_run.conclusion == 'success' && github.event.workflow_run.event == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          ref: ${{ github.event.workflow_run.head_sha }}
      # pnpm and Node setup, install, then the superseded check (id: head)
      - if: steps.head.outputs.superseded != 'true'
        run: pnpm release
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          GH_TOKEN: ${{ github.token }}
```

### `pnpm release` (`scripts/release.ts`)

The same steps run in CI and on the Mac. Each stops the release at the first problem, as today:

1. **The checkout:** fetch `origin/main`, then refuse unless the tree is clean and HEAD is `origin/main`. The old "the checkout is on main" check goes. CI checks out a commit, not a branch, and a clean HEAD at `origin/main` already means main's head.
2. **The gates:** refuse unless the CI workflow finished green on HEAD. That's today's `ciProblems`, unchanged. In CI the trigger already guarantees it, so there it's a cross-check.
3. **The build:** build without `CLOUDFLARE_ENV`, then refuse unless the built config passes `deployProblems`, unchanged.
4. **The upload (D14):** `wrangler versions upload --config <built config> --tag <full commit sha> --message "<sha7> <source>"`. Nothing goes live. Wrangler writes the new version's ID to its output file (`WRANGLER_OUTPUT_FILE_PATH`), and the release reads it from there.
5. **The restore point:** note the current UTC second, written like `2026-10-12T15:49:59Z`. Report it with the restore command (`pnpm admin pitr:restore --at <time>`) before anything goes live.
6. **The deploy:** `wrangler versions deploy <version-id>@100% --config <built config> --message "<sha7> restore point <time> <source>" --yes`. The source is `ci:<run id>` when `GITHUB_RUN_ID` is set, and `local` otherwise. Cloudflare caps a tag at 100 bytes and truncates a message at 1,000. A full SHA is 40 bytes, and both messages stay under 100.
7. **The report:** "Released `<sha7>` to the site", then "Open the app online on each phone, so its offline copy updates to this build."

Each report goes to stdout. When `GITHUB_STEP_SUMMARY` is set, it goes to the run summary too.

**Credentials, one per process:** the `git` calls get no token beyond the checkout's own credentials. `gh` gets `GH_TOKEN` in CI, or uses its own login on the Mac. Wrangler gets `CLOUDFLARE_API_TOKEN` in CI, or uses its own login on the Mac. `pnpm build` gets neither token and no `CLOUDFLARE_ENV`, because the build runs dependency code. Today's `withoutCloudflareEnv` grows into this. This guards against accidents, not against a malicious dependency. The whole job is the trust boundary, because code that runs earlier in the job can still reach the deploy step.

**Removed:**
- the export and `--skip-export`
- the bookmark, and `--first`, which existed only to skip the bookmark before the household existed; a first deploy now needs no flag
- `deploys.log`
- the release's loading of `.admin-token.env`

Their helpers go with them: `bookmarkFrom`, `exportProblem` and `deployLogLine` in `release-checks.ts`, and `releaseExportPath` in `admin-export.ts`.

## When things go wrong

- **A gate fails, or a newer push cancels CI:** the run doesn't conclude `success`, so nothing deploys.
- **`main` moved on before the deploy started:** step 3 of the workflow skips it green, and the newer commit deploys after its own CI.
  - **A push in the second between that check and the release's own fetch:** the release's checkout check refuses, and the run goes red. Nothing needs doing, because the newer commit deploys on its own.
  - **A push that lands later, during the build:** it doesn't stop the deploy. The older commit deploys, which is green, and the newer one follows after its own CI, because deploys run one at a time.
- **The deploy fails** (a Cloudflare error, a refused token): the run goes red and GitHub emails Andrew. Production stays on the previous version: a failed upload puts nothing live, and a failed `versions deploy` leaves its upload unused. Re-run the job, or run `pnpm release` from the main checkout, whose CI check passes because the gates passed.
- **A Durable Object class change:** `versions upload` refuses a commit with a pending Durable Object migration, and the run goes red before anything is live. The runbook deploys such a commit by hand with `wrangler deploy`.
- **A bad deploy:** the runbook's order becomes:
  1. `gh workflow disable deploy.yml`, so the next merge can't redeploy the bad code, then cancel any Deploy run already queued or running, which the switch doesn't stop.
  2. Roll back the code with `wrangler rollback <version-id>`, naming the version deployed just before the bad commit's, found by its message in `wrangler deployments list`. A later merge may sit on top of the bad one, so "the previous version" isn't enough.
  3. If the data is wrong too, take the bad deploy's restore point from its message, or from its Deploy run when it's older than the last 10 deploys, and run `pnpm admin pitr:restore --at <time>`. Code first, then data, for the reason the runbook already gives.
  4. Fix forward. Run `gh workflow enable deploy.yml` before merging the fix so the merge deploys it, or enable it after the merge and run `pnpm release`.
- **Renaming the CI workflow** would stop deploys silently, since `deploy.yml` names it. A unit test pins the two names together.
- **Re-running an older commit's CI on `main`** can cancel the newest commit's CI, since runs on `main` share one queue that cancels a run still going. Then nothing deploys main's head. The runbook says to re-run only the newest.

## Security

- **The token:** created in the Cloudflare dashboard, with the Workers Editor role on the `baby-tracker` Worker only and no expiry. Andrew saves it with `gh secret set CLOUDFLARE_API_TOKEN` in his own terminal, outside Claude Code, so it never passes through a chat or a transcript. If it ever leaks, revoke it in the dashboard, create another, and set the secret again.
- **Who sees it:** only the deploy job's last step gets the secret, and inside `pnpm release` only Wrangler's processes receive it. That protects against accidents. The job as a whole is the trust boundary, so its third-party action is pinned to a commit.
- **The accepted risk:** on a private repo on GitHub Free, a workflow on any branch could reference a repo secret. Only Andrew and his Claude sessions push branches here. The runbook says so.
- **Household data:** nothing about the household leaves the Mac. GitHub holds no admin token and no export.

## Testing

- **Unit tests** for the new pure functions:
  - the restore point's format
  - the upload's and the deploy's arguments, with both sources and Cloudflare's byte limits
  - the version ID read from Wrangler's output file, and the refusal when it holds none
  - the two reports
  - the reshaped checkout check: a clean HEAD at `origin/main` passes on any branch name or none, and a dirty tree or a different commit fails

  The existing `ciProblems` and `deployProblems` tests stay.
- **Unit tests on `deploy.yml`'s text:**
  - it listens for the workflow `ci.yml` names, so a rename can't silently stop deploys
  - the superseded check's wiring
  - every third-party action pinned to a commit
  - the 20-minute limit
- **All existing gates** stay green: pins, lint, typecheck, test, coverage, build, bundle check, e2e.
- **The live test:** `deploy.yml` only runs from the default branch, so nothing can exercise it before the merge. Its first run is M5.7's own merge (see Rollout).

## Rollout

1. **Before the merge,** Andrew creates the token and saves the `CLOUDFLARE_API_TOKEN` secret.
2. **Merge M5.7.** CI runs on the merge commit, and then the first automatic deploy runs. It ships M5.7, plus anything merged since the last `pnpm release`. That release was `b1714b7` (M3.5) at 23:05 UTC on 12 October 2026, after `79b8005` (M3.6) at 19:52 UTC.
3. **Watch the run.** It should end green, with the restore point and "Released …" in its summary. `wrangler deployments list` should show the restore point in the new deployment's message, and its version tagged with the merge commit. If Cloudflare refuses the token, nothing has gone live: check the token's scope against the runbook, set the secret again, and re-run the job.
4. **Open the app online on each phone.**
5. **After the merge:** update the release memories, whose "merged, ships on the next release" wording ends, and the roadmap.

**Done when:** a merge to `main` reaches production after its gates with nobody running anything. Its restore point is in Cloudflare's history and the run summary, a pull request's CI deploys nothing, and the runbooks describe the new flow.

## Out of scope

- Preview or staging deploys.
- Scheduled or automatic exports.
- Running the gates on the Mac when GitHub Actions is down.
- Workers Builds, the `cf` CLI, `wrangler-action`, and gradual deployments that split traffic between versions. M5.7 uses `wrangler versions upload` and `versions deploy` only to put one version live at 100 % (D14).
- Alerts beyond GitHub's failure email.

## Risks

- **The Custom Domain permission:** settled by D14. A deploy never touches the domain, so a token for one Worker is enough.
- **A Durable Object class change:** CI can't deploy one (D14). Its run fails red before anything goes live, and the runbook's hand deploy covers it.
- **A lagging API:** if GitHub's API still shows the CI run as in progress just after the `workflow_run` event, the release's CI check refuses and the run goes red. Re-running the job clears it. If it keeps happening, a follow-up adds a short wait.
- **Who gets the failure email:** GitHub emails the user a run is attributed to. The first deploy's run page shows who that is. If it isn't Andrew, the failure email doesn't reach him, and alerts need a second look.
- **YAML errors:** they show only on the first run, because `deploy.yml` can't run before the merge. Production stays on the previous version meanwhile, and `pnpm release` still deploys.
