# M1.9 Live Updates Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (chosen by Andrew on 9 Oct 2026) or superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A phone learns within moments which query keys the other phone's change touched. Each active caregiver's app holds a WebSocket to the household. After every saved or replayed change, every open socket hears `{"changed":[...]}`. Disabling a caregiver with `pnpm admin caregiver:disable` closes their sockets with 4401, and `caregiver:enable` lets them back.

**Architecture:** `packages/contracts` gains `socket.ts`: the socket's path, its heartbeat, the 4401 close, and `ChangedMessage`, the JSON a socket hears. In the Worker, a new `src/sockets.ts` holds the household's socket code:
- `HouseholdDO.fetch` passes `GET /api/ws` to `acceptSocket` before http-api sees the request. It checks the caller and accepts a hibernatable socket tagged with the caregiver's id.
- `setWebSocketAutoResponse` answers the heartbeat, so an idle socket never wakes the household.
- `mutations` takes a `Broadcast` and calls it once a change settles as `applied` or `replayed`.
- `disableCaregiver` and `enableCaregiver` are RPC methods on the household. `routeAdmin` reaches them at `POST /api/admin/caregiver/disable` and `/enable`, and `pnpm admin` posts to those routes.

**Tech Stack:** TypeScript 5.9.3, `effect` 4.0.1 (Schema, `effect/http`, `effect/http-api`), `@bt/contracts`, Workers and Durable Objects with WebSocket hibernation (`@cloudflare/workers-types` 5.20261006.1, wrangler 4.148.0, compatibility date 2026-10-06), `@cloudflare/vitest-plugin` 1.3.7, Vitest 4.1.11, Playwright 1.64.0, `@cloudflare/vite-plugin` 1.63.0, oxlint 1.87.0 + oxfmt 0.72.0, Node 24.21.0. ## Decisions this plan makes (veto in review)

- **P1: Every open socket hears every change, the caller's own included** (Andrew, 9 Oct 2026). §3.3 said "to all sockets except the caller's".
  - A parent with the app open on two devices, or a shared tablet signed in as them, then hears their own changes.
  - The calling phone also invalidates the same keys from its own answer, so it refetches once more. That costs one request per change.
  - Skipping only the calling device would need a connection id on every mutation: a header the Worker passes through and M1.10 sends. Two parents don't need that.
- **P2: `GET /api/ws` is not an http-api endpoint.** `HouseholdDO.fetch` takes it before http-api sees the request, as the M1.5 handoff said. It isn't in `Api` or `docs/api.json`.
  - The caller check runs first. A stranger, or a request with no `x-bt-email`, gets the contract's 401 whether or not it asked to upgrade.
  - An active caregiver who didn't ask to upgrade gets 426 with `upgrade: websocket`.
  - The socket is accepted with `ctx.acceptWebSocket` (hibernation, S7) and tagged `caregiver:<id>`. It carries no attachment: the tag is all that closing by caregiver needs.
- **P3: A socket hears `{"changed":[...]}`**, which contracts names `ChangedMessage`. The keys are the ones the change's own answer carries.
  - It hears them after `applied`, and again after `replayed`, so a retry repairs a broadcast lost with the first answer (§3.3, AC 14).
  - It never hears about `rejected`, `replay-mismatch` or `other-route`. `settle` succeeds for exactly the first two outcomes, so `mutations` broadcasts what `settle` returns.
  - `householdApi(storage, broadcast)` passes the broadcast to both handler groups. A plain parameter is enough for one function.
- **P4: The household answers the heartbeat without waking.** `setWebSocketAutoResponse` answers `ping` with `pong`, and a hibernated household stays asleep, with no duration billed.
  - Cloudflare closes a socket that carries nothing for a while, so M1.10's client must send the heartbeat.
  - The household defines no `webSocketMessage`. Anything else a client sends is ignored, and the socket stays open.
- **P5: The household answers a client's close** (changed in the final review; this plan first said no handler was needed).
  - `web_socket_auto_reply_to_close`, on from compatibility date 2026-04-07, doesn't cover hibernatable sockets in workerd 1.20261006.1. Without a handler, a client's own close ended as 1006 "WebSocket disconnected without sending Close frame." after up to 1.5 s.
  - `webSocketClose` calls `answerClose` in `sockets.ts`. While the socket is `CLOSING`, it echoes the client's code and reason. A close with no code (1005), or 1006, gets an answer without a code, since `close()` refuses those codes.
  - The socket then leaves `getWebSockets()`. The tests in "a client closing its socket" pin the codes the client sees (1000, 4000, and 1005 for no code).
- **P6: Only open sockets are sent to or closed.** A socket the household closed stays in `getWebSockets()` as `CLOSING` until the phone answers.
  - A phone asleep in a pocket may not answer for minutes.
  - `send()` on such a socket throws `TypeError: Can't call WebSocket send() after close().` The other parent's change would answer 500 although it was saved, and so would every retry of it. The prototype showed this.
  - A close counts only the sockets it closes now, so disabling twice reports 0 the second time.
- **P7: Disabling and enabling a caregiver.** Disabling is D6. Andrew added enabling on 9 Oct 2026, since the seed runs once and nothing else could undo a disable.
  - `POST /api/admin/caregiver/disable` and `/enable` take `{ email }`, checked like the seed's emails: lowercase, with one `@`.
  - They call `disableCaregiver(email)` and `enableCaregiver(email)` on the household.
  - Both answer 200 with `{ email, active, closedSockets }`, 404 for an email that isn't a caregiver, and 400 for a bad body. Any other method gets 404, as the seed's route does.
  - Disabling sets `active = 0`, stamps `updated_at`, and closes the caregiver's open sockets with 4401 "caregiver disabled". Their next request and next upgrade get 401 (AC 10). The other parent's sockets stay open.
  - Enabling sets `active = 1` and stamps `updated_at`. No socket comes back: the phone reconnects on its own (M1.10).
  - Both can run twice harmlessly. Caregivers have no `updated_by`, since the admin isn't a caregiver.
- **P8: `pnpm admin caregiver:disable <email>` and `caregiver:enable <email>`.** Each takes one email, trimmed and lowercased like the seed's. It posts the email with the service token, as `household:seed` does.
- **P9: Waking leaves the prune alarm where it was.** Hibernation makes waking routine: every message to a hibernated household runs its constructor again.
  - A test pins `startHousehold`'s "only when no alarm is set" guard (the M1.5 handoff). An evicted household woken 3 h later keeps its alarm.
  - Without the guard, each wake would push pruning back.
- **P10: An upgrade passes through `routeApi` intact.** `new Request(request, { headers })` carries `upgrade: websocket` to the household, and the 101 comes back with its socket (the M1.4 handoff).
  - An E2E test opens a socket through `vite preview` with `access.dev`, and the household answers its heartbeat, on WebKit and Chromium.
  - No E2E test writes data.
- **P11: The Worker bundle grows from 250.26 to about 251.2 KiB gzip**, well under the 400 KiB budget.

## Review Focus

1. **A save right after a disable, while the disabled phone hasn't answered the close.** A phone asleep in a pocket may not answer for minutes. Expect the other parent's save to answer 201 and her socket to hear it, not a 500 for a change that was saved. Tested in Task 4.
2. **A retry whose answer was lost** (AC 14). Expect the other phone to hear the change again, so a broadcast lost with the first answer is repaired. Tested in Task 3.
3. **A household evicted from memory while sockets are open** (hibernation, S7). Expect the sockets to stay open, to hear later changes, and to close on a disable. Expect the prune alarm to stay where it was. Tested in Tasks 2, 3 and 4.
4. **A disabled parent** (AC 10). Expect every socket of theirs closed with 4401, their next request and upgrade refused, and the other parent untouched. Expect `caregiver:enable` to let them back. Tested in Task 4.
5. **A change the household refuses.** Expect no socket to hear about a 400 or a 409, so no phone refetches for nothing. Tested in Task 3.

import { invalidInputFrom, NotFound } from "@bt/contracts"
import { Result, Schema } from "effect"
import { errorResponse } from "./error-response.ts"
import { Email, type HouseholdSeed, HouseholdSeed as Seed, type SeedResult } from "./seed.ts"

export interface CaregiverStatus {
  readonly email: string
  readonly active: boolean
  readonly closedSockets: number
}

export interface AdminHousehold {
  seedHousehold(seed: HouseholdSeed): Promise<SeedResult>
  disableCaregiver(email: string): Promise<CaregiverStatus | undefined>
  enableCaregiver(email: string): Promise<CaregiverStatus | undefined>
}

type AdminRoute = (request: Request, household: AdminHousehold) => Promise<Response>

const decodeSeed = Schema.decodeUnknownResult(Schema.fromJsonString(Seed), { errors: "all" })

const decodeCaregiver = Schema.decodeUnknownResult(Schema.fromJsonString(Schema.Struct({ email: Email })), {
  errors: "all",
})

const noStore = { "cache-control": "no-store" }

const seed: AdminRoute = async (request, household) => {
  const decoded = decodeSeed(await request.text())
  if (Result.isFailure(decoded)) return errorResponse(invalidInputFrom(decoded.failure.issue))
  const result = await household.seedHousehold(decoded.success)
  return Response.json(result, { status: result.created ? 201 : 200, headers: noStore })
}

const caregiverRoute =
  (change: (household: AdminHousehold, email: string) => Promise<CaregiverStatus | undefined>): AdminRoute =>
  async (request, household) => {
    const decoded = decodeCaregiver(await request.text())
    if (Result.isFailure(decoded)) return errorResponse(invalidInputFrom(decoded.failure.issue))
    const status = await change(household, decoded.success.email)
    return status === undefined ? errorResponse(new NotFound()) : Response.json(status, { headers: noStore })
  }

const ROUTES = new Map<string, AdminRoute>([
  ["POST /api/admin/household", seed],
  ["POST /api/admin/caregiver/disable", caregiverRoute((household, email) => household.disableCaregiver(email))],
  ["POST /api/admin/caregiver/enable", caregiverRoute((household, email) => household.enableCaregiver(email))],
])

export const routeAdmin = async (request: Request, household: AdminHousehold): Promise<Response> => {
  const route = ROUTES.get(`${request.method} ${new URL(request.url).pathname}`)
  return route === undefined ? errorResponse(new NotFound()) : route(request, household)
}
