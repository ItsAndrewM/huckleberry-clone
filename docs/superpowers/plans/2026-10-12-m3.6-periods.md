# M3.6 Day, Week and Month Reads Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (chosen by Andrew on 12 Oct 2026) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The household answers any day, week or month: its bounds in the household's zone, when it answered, its totals (and, for a week or a month, each day's), and every feed, diaper and measurement in it. The calendar (M3.7, M3.8), the trends (M3.10) and M5.5's latency check read these answers. When the household's time zone changes, the phone refreshes every day, week and month it has cached.

**Architecture:**
- **`packages/domain`:** `time/calendar.ts` gains a week's seven dates and a month's dates. A new `aggregate/periods.ts` says whether a feed touches a period through one of its parts (`feedTouches`), totals each day of a period with M1.8's `totalsIn` (`totalsByDay`), and adds days into the period's totals (`sumTotals`).
- **`packages/contracts`:** a new `periods.ts` holds the answers (`DayPeriod`, `WeekPeriod`, `MonthPeriod`, with `PeriodBounds` and `DayTotals`) and the `periods` group.
- **`apps/worker`:** the reads narrow by session bounds in SQL, and the domain decides what's in a period: `liveFeedsTouching`, `liveDiapersIn` and `liveMeasurementsIn`. Then `core/periods.ts` answers a day, a week or a month, and `period-handlers.ts` serves them.
- **`apps/web`:** `api/zone-change.ts` watches the query cache, and invalidates every cached day, week and month when `me`'s time zone changes.

**Tech Stack:** TypeScript 5.9.3, `effect` 4.0.1 (Schema, `effect/http-api`), `@bt/contracts` and `@bt/domain`, Workers and Durable Objects (`@cloudflare/workers-types` 5.20261006.1, wrangler 4.148.0), `@cloudflare/vitest-plugin` 1.3.7, TanStack Query 5.104.1, Vitest 4.1.11, fast-check 4.10.2, Playwright 1.64.0, oxlint 1.87.0 and oxfmt 0.72.0, Node 24.21.0. M3.6 adds no package.

## Decisions this plan makes (veto in review)

- **P1: Three endpoints in a `periods` group, after M3.11's `export` group.**
  - `GET /api/days/:date`, `GET /api/weeks/:week` and `GET /api/months/:month`. The params are the contract's `LocalDate`, `IsoWeek` and `YearMonth`, so a week runs Monday to Sunday (Andrew, 12 Oct 2026). The week param refines `IsoWeek`: a week whose days all fall within 1999 to 2100, so 2100-W52 answers 400.
  - The client calls `client.periods.day({ params: { date } })`, `.week({ params: { week } })` and `.month({ params: { month } })`. The M3.6 row said `/weeks/:isoWeek`; the param is `week`, beside `date` and `month`.
  - A param that isn't a real date, week or month, or falls outside 1999 to 2100, answers 400 `InvalidInput` naming it. A stranger gets 401 before the param is read.
  - Each answer reads the clock once, as the request comes in.
- **P2: Every period answers its bounds, when the household answered, its totals and its records. A week and a month also answer each of their days** (Andrew, 12 Oct 2026, over the recommended days and weeks only).
  - `DayPeriod`: `{ date, bounds, asOf, totals, feeds, diapers, measurements }`.
  - `WeekPeriod`: `{ week, bounds, asOf, totals, days, feeds, diapers, measurements }`, with seven `days`, Monday first.
  - `MonthPeriod`: `{ month, bounds, asOf, totals, days, feeds, diapers, measurements }`, with 28 to 31 `days`.
  - Each day is `DayTotals`: `{ date, bounds, totals }`. Every `totals` is M1.8's `Totals`.
  - There are no averages, and no flag for a partial period, a day before the birth date or a day after today. M3.10 works those out from `asOf`, the birth date in `/api/me`, and the records.
- **P3: A record is in a period when one of its parts is** (M1.7's handoff).
  - **A feed** is in when one of its live segments overlaps `[start, end)`, a running one reaching `asOf`, or starts in it, or when one of its live bottles is at a time in `[start, end)`.
    - A segment's start counts on its own, so a side a phone started ahead of the clock is in its day before any time has run (AC 21), as M1.8 counts its feed.
    - So a bottle-only feed counts like a diaper, and a bottle at exactly midnight belongs to the day that begins.
    - A feed that ended exactly as a day began isn't in that day, though its session's end touches it.
    - A paused feed whose parts all lie before the period isn't in it, though it's still the active feed.
  - **A diaper or a measurement** is in when its time is in `[start, end)` (M4.3's handoff).
  - **Only live records and live parts count.** A deleted feed, segment, bottle, diaper or measurement is left out, and so is a feed whose only part in the period was deleted.
  - **Records come whole:** every live segment and bottle of each feed, unclipped, and a running segment's `endedAt` still null, as `/today` sends them. M3.7 draws a feed across midnight and a running feed from them.
  - **Order:** feeds by when they started, diapers and measurements by their time.
- **P4: Totals follow M1.8's rules, day by day. A week's and a month's totals are the sum of their days'.**
  - A feed counts on the day it started. Nursing counts by each live segment's overlap with the day, a running side up to `asOf`. A bottle counts at its time, a diaper at its time.
  - Adding the days means a table of days always adds up to its total. Each day's seconds are rounded down first, as `totalsIn` does, so a side that crossed midnight mid-second counts up to a second short a day against the period's exact time.
  - mL are added in tenths, so 0.1 mL and 0.2 mL make 0.3 mL.
- **P5: Bounds are whole milliseconds, not `Instant`s.**
  - `PeriodBounds` is `{ start: Schema.Int, end: Schema.Int }`, half-open, so a 23- or 25-hour day comes out as it is (AC 23).
  - The params accept 1999 to 2100, as the contract's calendar types do, and a day at either end of that range begins or ends outside `Instant`'s 2000 to 2099. With `Instant` bounds, such a request would fail to encode and answer 500.
  - `asOf` and every record keep `Instant`.
- **P6: The domain owns the rules.**
  - `aggregate/periods.ts` holds `feedTouches(period, feed, now)`, `totalsByDay(dates, zone, feeds, diapers, now)` and `sumTotals(days)`. `time/calendar.ts` gains `isoWeekDates(week)` and `monthDates(month)`.
  - They're pure and held to 100 % coverage.
  - The M3.6 row's property test: across clock changes in the ten property zones, with a side sometimes still running, a week's days and a month's days add up to `totalsIn` over the whole period. Times are whole minutes there, so every day's seconds are whole and the sums are exact.
- **P7: The Worker narrows by session bounds in SQL, and the domain decides.**
  - `liveFeedsTouching` selects the live feeds with `started_at < end AND (ended_at IS NULL OR ended_at >= start)`. SQLite can range-scan `feeds_by_time` on `started_at`, but it still reads every earlier feed's `ended_at`, as `/today`'s read does (M1.8's P7). It loads each feed whole with `loadFeed`, and keeps those `feedTouches` accepts.
  - `liveDiapersIn` and `liveMeasurementsIn` select `[start, end)` on their time indexes.
  - Each feed loads its segments and bottles with their own queries, as `/today` and M3.11's export do. M5.5 times a month with two years of data.
- **P8: A time zone change refreshes every cached day, week and month on the phone** (M1.15's handoff).
  - `api/zone-change.ts` watches the query cache. When `me`'s `household.timeZone` differs from the zone it last saw, it invalidates the `day`, `week` and `month` prefixes, once.
  - That covers this phone's own save, which writes `me` through `rememberSaved`, and the other phone's change, whose `changed` keys refetch `me`.
  - The first `me` of a session changes nothing, since nothing was cached in another zone.
  - The server's `changed` keys stay as they are. A zone change could have sent new keys such as `["day"]`, but an installed app on older code decodes the settings save's `changed` with its own `QueryKey` union. A member it doesn't know would fail that decode, and a zone change that saved would look like an error on that phone (M1.8's P11).
- **P9: M3.6 adds no web queries.** M3.7 adds the first period query (`api/day.ts`, session 54), so M5.4's handoff, that a query showing the current period turns over at the household's midnight, moves to M3.7's row. M3.8's and M3.10's queries follow M3.7's.
- **P10: Sleep and supplements join as added fields.** An installed app reading a later version's answer ignores a field it doesn't know, such as M3.1's sleeps (the contract test pins it). Records are one list per kind, never a union of kinds, so no union gains a member.
- **P11: The Worker bundle grows from 260.05 to 261.05 KiB gzip,** well under the 400 KiB budget. The app grows by the zone watch alone.

## Review Focus

The five ways this is most likely to fail a parent, each with the test that pins it:

1. **A feed across midnight** (AC 4). Expect it whole in both days, counted on the day it started, and each day's minutes its own. Pinned by `periods.test.ts` in the domain ("gives each date its bounds in the zone and its own totals, counting the AC 4 feed on the day it started", Task 1) and `periods-core.test.ts` ("holds a feed across midnight whole in both days, and counts it on the day it started (AC 4)", Task 3).
2. **A feed still running.** Expect it in today with its side still open, its time counted up to when the household answered and growing with each request, and not in tomorrow. Pinned by `periods-core.test.ts` ("holds a running feed with its side still open, …", Task 3) and the Worker's `periods.test.ts` ("answers a running feed whole, its time growing with the household's clock", Task 4).
3. **Midnight itself.** Expect a bottle, a diaper or a measurement at exactly midnight to belong to the day that begins, and a feed that ended exactly at midnight to stay in the day before. Pinned by `feedTouches`' table (Task 1) and `periods-core.test.ts` ("holds a bottle, a diaper and a measurement at the day's first moment, …" and "leaves a feed that ended as the day began to the day before, …", Task 3).
4. **Something the other parent deleted:** a feed, a segment, a bottle, a diaper or a measurement. Expect it gone from the records and the totals, and a feed whose only part in the day was deleted gone too. Pinned by `periods-core.test.ts` ("leaves out whatever was deleted, and a feed whose only part in the day was", Task 3).
5. **The household's day, not UTC's or the phone's.** Expect a 25-hour day to keep all 25 hours (AC 23), a week's days to add up to the week across a clock change, and no cached day kept in the old zone after the household's zone changes. Pinned by the property test (Task 1), `periods-core.test.ts` ("takes the day in the household's zone, …", Task 3) and `zone-change.test.ts` (Task 5).

import { contains, overlaps } from "../interval/interval.ts"
import type { LocalDate } from "../time/calendar.ts"
import type { Instant, Interval } from "../time/instant.ts"
import type { TimeZone } from "../time/zone.ts"
import { zonedDayBounds } from "../time/zoned.ts"
import { type DiaperChange, type StartedFeed, type Totals, totalsIn } from "./totals.ts"

export interface DayTotals {
  readonly date: LocalDate
  readonly bounds: Interval
  readonly totals: Totals
}

export const feedTouches = (period: Interval, feed: StartedFeed, now: Instant): boolean =>
  feed.segments.some(
    (segment) =>
      contains(period, segment.startedAt) ||
      overlaps({ start: segment.startedAt, end: segment.endedAt ?? now }, period),
  ) || feed.portions.some((portion) => contains(period, portion.occurredAt))

const tenths = (ml: number) => Math.round(ml * 10)

export const sumTotals = (days: ReadonlyArray<Totals>): Totals => {
  const sum = (pick: (totals: Totals) => number) => days.reduce((total, totals) => total + pick(totals), 0)
  const sumMl = (pick: (totals: Totals) => number) => sum((totals) => tenths(pick(totals))) / 10
  return {
    feedsStarted: sum((totals) => totals.feedsStarted),
    leftSeconds: sum((totals) => totals.leftSeconds),
    rightSeconds: sum((totals) => totals.rightSeconds),
    nursingSeconds: sum((totals) => totals.nursingSeconds),
    breastMilkMl: sumMl((totals) => totals.breastMilkMl),
    formulaMl: sumMl((totals) => totals.formulaMl),
    bottleMl: sumMl((totals) => totals.bottleMl),
    diapers: sum((totals) => totals.diapers),
    wetDiapers: sum((totals) => totals.wetDiapers),
    dirtyDiapers: sum((totals) => totals.dirtyDiapers),
  }
}

export const totalsByDay = (
  dates: ReadonlyArray<LocalDate>,
  zone: TimeZone,
  feeds: ReadonlyArray<StartedFeed>,
  diapers: ReadonlyArray<DiaperChange>,
  now: Instant,
): DayTotals[] =>
  dates.map((date) => {
    const bounds = zonedDayBounds(date, zone)
    return { date, bounds, totals: totalsIn(bounds, feeds, diapers, now) }
  })

import type { DayPeriod, MonthPeriod, WeekPeriod } from "@bt/contracts"
import {
  type Instant,
  type Interval,
  type IsoWeek,
  isoWeekBounds,
  isoWeekDates,
  type LocalDate,
  monthBounds,
  monthDates,
  sumTotals,
  type TimeZone,
  totalsByDay,
  type YearMonth,
  zonedDayBounds,
} from "@bt/domain"
import { calendarOf } from "./calendar.ts"
import { liveDiapersIn } from "./diapers.ts"
import { liveFeedsTouching } from "./feeds/reads.ts"
import { liveMeasurementsIn } from "./growth.ts"

const read = (sql: SqlStorage, zone: TimeZone, bounds: Interval, dates: ReadonlyArray<LocalDate>, now: Instant) => {
  const feeds = liveFeedsTouching(sql, bounds, now)
  const diapers = liveDiapersIn(sql, bounds)
  const days = totalsByDay(dates, zone, feeds, diapers, now)
  const totals = sumTotals(days.map((day) => day.totals))
  return { days, period: { bounds, asOf: now, totals, feeds, diapers, measurements: liveMeasurementsIn(sql, bounds) } }
}

export const dayOf = (sql: SqlStorage, date: LocalDate, now: Instant): DayPeriod => {
  const { zone } = calendarOf(sql)
  return { date, ...read(sql, zone, zonedDayBounds(date, zone), [date], now).period }
}

export const weekOf = (sql: SqlStorage, week: IsoWeek, now: Instant): WeekPeriod => {
  const { zone } = calendarOf(sql)
  const { days, period } = read(sql, zone, isoWeekBounds(week, zone), isoWeekDates(week), now)
  return { week, ...period, days }
}

export const monthOf = (sql: SqlStorage, month: YearMonth, now: Instant): MonthPeriod => {
  const { zone } = calendarOf(sql)
  const { days, period } = read(sql, zone, monthBounds(month, zone), monthDates(month), now)
  return { month, ...period, days }
}

import { type Me, queryKeys } from "@bt/contracts"
import type { QueryClient } from "@tanstack/react-query"

const PERIOD_PREFIXES = [["day"], ["week"], ["month"]]

export const refreshPeriodsOnZoneChange = (queryClient: QueryClient) => {
  const zoneOf = () => queryClient.getQueryData<Me>(queryKeys.me)?.household.timeZone
  let zone = zoneOf()
  queryClient.getQueryCache().subscribe(() => {
    const next = zoneOf()
    if (next === undefined || next === zone) return
    const moved = zone !== undefined
    zone = next
    if (moved) for (const queryKey of PERIOD_PREFIXES) void queryClient.invalidateQueries({ queryKey })
  })
}
