# M5.7 Continuous Deploy Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (native, as Andrew chose on 12 Oct 2026, stopping at PR + CodeRabbit with no merge) to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** every push to `main` deploys to https://baby.andamonium.dev once CI's `check` and `e2e` pass on that commit, with nobody running anything. `pnpm release` stays as the manual fallback and runs the same script.

**Architecture:**
- **`.github/workflows/deploy.yml` (new):** starts when the `CI` workflow completes on a push to `main`, and runs only if that run passed. It checks out the commit CI tested and installs. If `main` has moved on by then, it ends green with a notice. Otherwise it runs `pnpm release` with the Cloudflare token and the job's GitHub token.
- **`scripts/release.ts` (reshaped):** refuses unknown flags, fetches `origin/main`, checks the checkout and CI, builds, checks the built config, then deploys with the restore point and the commit as the version's metadata. It prints a report, and writes it to the run summary in CI.
- **`scripts/release-checks.ts` (reshaped):** stays the pure, tested half. It holds the checks, `envFor`, which gives each child process only its own credential, the restore point, Wrangler's arguments and the report.
- **Removed:** the export, the bookmark, `--first`, `--skip-export`, `deploys.log`, and the release's loading of `.admin-token.env`.

**Tech Stack:** Node 24.21.0 running `.ts` directly, Vitest 4.1.11, Wrangler (the catalog's pinned version, which takes `--tag` and `--message`), GitHub Actions (`actions/checkout@v7`, `pnpm/action-setup@v6`, `actions/setup-node@v7`, as `ci.yml` uses), `gh` 2.x. M5.7 adds no package.

**Spec:** `docs/superpowers/specs/2026-10-12-m5.7-continuous-deploy-design.md`, approved by Andrew on 12 Oct 2026. Read it with this plan: its Decisions table is the why behind every task.

**Andrew's decisions (12 Oct 2026, from his grill; the spec's table numbers them the same):**
- **D1, the deploy path:** GitHub Actions running the repo's pinned Wrangler, not Workers Builds, which can't wait for GitHub's checks.
- **D2, the trigger:** a separate `deploy.yml` on `workflow_run`, not a job inside `ci.yml`.
- **D3, the data protection:** a restore point, the UTC second before `wrangler deploy`, instead of a bookmark or an export. No household credential or data goes to GitHub.
- **D4, a superseded commit:** skip, with a notice, and end green.
- **D5, pausing:** `gh workflow disable deploy.yml`, then `gh workflow enable deploy.yml`.
- **D6, the record:** Cloudflare's deployment history. The tag is the commit, and the message holds the restore point. The run summary repeats it, and `deploys.log` is retired.
- **D7, the token:** the Workers Editor role on the `baby-tracker` Worker alone, never expiring. D14 (after the final review, see the build record) keeps deploys off the Custom Domain, so no zone permission is needed.
- **D8 and D9, the fallback:** `pnpm release` stays, running the same script, and it still needs green CI on the commit.
- **D10:** docs-only pushes deploy too.
- **D11:** exports are taken by hand only.
- **D12:** alerts are GitHub's failure email.
- **D13:** the iPhone device checklist runs after a deploy whose PR says "device checklist after deploy".

## Decisions this plan makes (veto in review)

- **P1, one credential per process.** `envFor(tool, env)` drops these:
  - **`git`:** `CLOUDFLARE_ENV`, `CLOUDFLARE_API_TOKEN`, `GH_TOKEN` and `GITHUB_TOKEN`, since the checkout carries its own credentials
  - **`gh`:** `CLOUDFLARE_ENV` and `CLOUDFLARE_API_TOKEN`. It keeps both GitHub tokens, since `gh` reads either.
  - **`build`:** the same four as `git`
  - **`wrangler`:** `CLOUDFLARE_ENV` and both GitHub tokens

  It replaces `withoutCloudflareEnv`.
- **P2, the fetch names its refspec.** `git fetch --quiet origin +refs/heads/main:refs/remotes/origin/main`. CI's checkout of a single commit may have no `origin/main` to update otherwise. Measured locally: it updates `origin/main`.
- **P3, the checkout check's wording.** It drops "the checkout is on main" and keeps "the checkout has no uncommitted changes". Its other check now reads "HEAD is the same commit as origin/main".
- **P4, flags are still refused.** `refuseUnknownFlags` runs `parseArgs` strictly with no options. So `pnpm release --skip-export`, from an old note, fails with "Unknown option" instead of deploying. It's tested as a pure function.
- **P5, `account_id is pinned`.** A new deploy check. CI's token for one Worker can't look up its account, and a missing `account_id` could also send a deploy from the Mac to another account Wrangler is logged into. The committed `wrangler.jsonc` passes it.
- **P6, the message and the tag.**
  - **The message:** `<first 7 of the commit> restore point <YYYY-MM-DDTHH:MM:SSZ> <ci:GITHUB_RUN_ID | local>`, about 60 bytes.
  - **The tag:** the full 40-character commit.
  - **Order:** both go after `--config <built config>`.
- **P7, the report.** Three paragraphs, separated by blank lines, so the run summary's Markdown keeps them apart:
  1. "Released `<sha7>` to the site."
  2. "Restore point: `<time>`." with the restore command in backticks
  3. the phones line from before

  It goes to stdout, and is appended to `GITHUB_STEP_SUMMARY` when that's set.
- **P8, the workflow's details.**
  - It installs before the superseded check, so only a second or so passes between that check and the release's own fetch.
  - The check runs with `shell: bash`, which sets `-eo pipefail`, and `git ls-remote --exit-code`. So a failed lookup fails the run red, rather than skipping green.
  - The two custom steps are named "Skip if main has moved on" and "Deploy".
  - `WRANGLER_SEND_METRICS` is `"false"`, as in `ci.yml`.
- **P9, the workflow's tests read its text.** There's no YAML parser in the repo, and M5.7 adds no package. `scripts/workflows.test.ts` pins six facts:
  - the `CI` name in both files
  - the job's condition
  - the `head_sha` checkout
  - `bash` and `--exit-code`
  - that the secret appears exactly once, after `run: pnpm release`
  - `cancel-in-progress: false`
- **P10, the docs.**
  - §1 of the implementation plan gains a `.github/workflows/` line.
  - The runbook gains "The deploy token", "Deploys", "Deploying by hand" and "Pausing deploys".
  - "First deploy" keeps its steps, marked done on 10 Oct, with `pnpm release` from the Mac and a new deploy token for a new Worker.
  - `docs/spike-results.md` and the M1.16 row stay as records.

## Review Focus

The inputs and conditions most likely to bite that the spec implies but doesn't spell out, each with the test that pins it:

1. **The Cloudflare token reaching dependency code** during the install or the build. Task 1, "gives the build no token and no CLOUDFLARE_ENV, since it runs dependency code and must build production", and Task 2, "hands the Cloudflare token to the release step alone, after the install".
2. **Deploying a commit CI didn't test.** A `workflow_run` job's own `github.sha` is main's latest commit. Task 2, "checks out the commit CI tested, not main's latest".
3. **An old CI run, re-run after `main` moved on, rolling production back.** Task 1, "refuses a commit behind or ahead of origin/main, such as an old CI run re-run after main moved on". The workflow's superseded step skips such a run green before that.
4. **Renaming the CI workflow, which would stop deploys silently.** Task 2, "waits for the workflow ci.yml names, the one pnpm release asks gh about, so a rename can't stop deploys silently".
5. **A restore point the restore command can't take.** Task 1, "is a time pnpm admin pitr:restore --at takes, at that same second".

Two more, also pinned: a failed `ls-remote` skipping green (Task 2, "fails, rather than skipping green, when it can't read main's head"), and an unpinned account (Task 1, "refuses an empty account_id, which CI's token for one Worker can't look up").
