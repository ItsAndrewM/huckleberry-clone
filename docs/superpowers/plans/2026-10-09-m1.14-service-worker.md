# M1.14 Service Worker Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (chosen by Andrew on 9 Oct 2026) or superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An installed phone opens the app from a saved copy when there's no network, and says so. Neither the household's data nor Sign in is ever answered from that copy. The app also gets a manifest and a home-screen icon, so both phones can install it at M1.16.

**Architecture:**
- **The worker:** `apps/web/src/service-worker/sw.ts`, about 30 lines. Its decisions live in two pure modules that Node tests reach:
  - `routes.ts` decides who answers a request.
  - `shell-cache.ts` answers pages and assets, from the network or the saved copy.
- **The build:** a small Vite plugin, `apps/web/service-worker-build.ts`. It adds the worker as a second entry of the client build, named `sw.js`, and writes in the build's version and the files to save.
- **Registration:** `src/service-worker/register.ts` registers it from `main.tsx`, in production builds only.
- **Install files:** `public/` gains the manifest and the icons. `index.html` links them.

**Tech Stack:** TypeScript 5.9.3, Vite 8.3.3 (Rolldown), `@cloudflare/vite-plugin` 1.63.0, React 19.3, Vitest 4.1.11, Playwright 1.64.0 (WebKit and Chromium), oxlint 1.87.0 and oxfmt 0.72.0, Node 24.21.0. No new dependency.

## Decisions this plan makes (veto in review)

- **P1: AC 11's full flow moves to M1.12** (Andrew, 9 Oct 2026).
  - The M1.14 row asked for "open, show the last Today, keep the form, Retry once". Today is M1.11 and the forms are M1.12, so M1.12, the last of the three to land, owns the whole flow.
  - M1.14's E2E covers what the worker owns: the app and any tab's address open offline, and `/api/*` and Sign in always reach the network.
- **P2: The worker is ours, with no new dependency.**
  - It is the spike's `sw.js` (S4) in TypeScript: about 30 lines of wiring over two tested modules.
  - Workbox, through `vite-plugin-pwa`, would bring a large build-time dependency tree for the same three rules.
- **P3: `sw.js` is a second entry of the client build.**
  - The plugin sets the client environment's inputs to `index.html` and `src/service-worker/sw.ts`, and names the second `sw.js` at the root, so its scope is the whole app.
  - Nothing else imports the worker's modules, so Rolldown emits it as one file with no `import` or `export`: a classic script, which every browser's service worker accepts.
  - If the app ever imports `routes.ts` or `shell-cache.ts`, Rolldown would move them into a shared chunk, and `sw.js` would gain an `import`. A classic worker can't run that, so `offline.spec.ts` would fail.
  - The file names to save exist only once the bundle is written. So in `generateBundle` (order `post`, after Vite has emitted `index.html`), the plugin puts `const SHELL = {"version":…,"urls":[…]}` before the worker's code.
  - `sw.ts` declares `SHELL`, so it type-checks.
  - The main bundle's hash didn't change in the prototype.
- **P4: The worker saves the build's shell: `/` and every file under `assets/`.**
  - It saves `/`, not `/index.html`. Static Assets redirects `/index.html` to `/`, and browsers refuse a redirected response for a navigation.
  - It doesn't save the manifest, the icons, `sw.js` or `.assetsignore`. A phone needs those only while installing, signed in.
  - It fetches each with `cache: "no-cache"`. The HTTP cache can't hand it an old page, and an unchanged hashed asset comes back as a 304.
  - **Each file must arrive as itself, or nothing is saved** (added in the final review).
    - Install fetches each file with `redirect: "error"` and saves the build only if every file answers OK and unredirected, with HTML at `/` and nowhere else, and `/` loads only files this build saves (`build-files.ts`).
    - Otherwise the install fails and logs why, and the browser keeps the previous worker and its copy.
    - Without this, a deploy that landed mid-install saved the app's fallback page as the build's JS and CSS, deleted the good copy, and the next offline launch was blank. The silent-failure review reproduced that in both engines.
- **P5: How the worker answers.**
  - **`/api/*`, a request that isn't a GET, or another origin:** it stays out. The household's reads and saves, Sign in (a top-level navigation to `/api/login`) and Access's pages always reach the network (D1, the M1.10 handoff).
  - **A navigation:** the network first. Whatever the network answers passes through untouched, Access's 302 to sign in and a 503 included, so an expired session still reaches Access (S3). Only when the network can't be reached does the worker open the saved `/`, and the router shows the address's tab.
  - **Any other same-origin GET:** the saved copy first, then the network.
  - **Matching saved files:** the worker matches with `ignoreVary`.
    - Vite's preview server answers `Vary: Origin` (its CORS middleware). Chromium sends `Origin` on module scripts and `crossorigin` stylesheets, and the saved entries have none. This plan first blamed Static Assets; the final review corrected it, since Cloudflare documents no `Vary` there.
    - Without `ignoreVary`, the prototype's offline reload on Chromium got the shell but no JS or CSS.
    - The saved files are this origin's own hashed files, so `Origin` can't change them, and production loses nothing.
  - **A saved copy that can't be read** (added in the final review):
    - Pages never read the saved copy before the network.
    - An asset whose saved copy can't be read comes from the network, and the failure is logged.
    - The worker reads through `caches.match` with its build's cache name, so a read never creates a cache.
    - Before this, a Cache Storage failure failed every page and asset while online, and only deleting the home-screen app would have recovered.
  - **No time limit on the network** (questioned in the final review, kept for Andrew to decide). On one bar or dead Wi-Fi a page waits as long as the network does, as it does without a worker. Racing the network against about 3 s would open the saved app sooner. See the handoff.
- **P6: Each build has its own cache, and a new build replaces the old one.**
  - **Cache name:** `bt-shell-<version>`, where the version is the first 16 hex characters of the SHA-256 of the saved URLs and `index.html`.
  - **Install:** a deploy changes `sw.js`, so the browser installs the new worker, which saves the new build. This happens only while signed in, since Access gates `/sw.js` (S4).
  - **Activate:** the new worker takes over at once (`skipWaiting`, `clients.claim`), as the spike's did. It then deletes every other `bt-shell-` cache and leaves caches it didn't make.
  - **An open page** keeps the JS it already loaded. The app has no lazy chunks today (see the M5.5 handoff).
- **P7: The app registers `/sw.js` with scope `/`, after `load`, in production builds only.**
  - `pnpm dev` stays free of a worker.
  - A refused registration leaves the app running without a saved copy, and says nothing, since there is nothing for a parent to do. That covers private browsing, blocked storage and signed out while registering.
  - Playwright's block isn't a refusal: it replaces `register` with a no-op that resolves (corrected in the final review). So only `service-worker-register.test.ts` covers a refused registration.
  - `registerServiceWorker` answers `registered` or `unavailable` and never rejects. It still throws where `navigator.serviceWorker` is missing, as in an in-app browser (a deferred minor).
- **P8: `sw.ts` is type-checked with the WebWorker library, in `apps/web/tsconfig.sw.json`.**
  - DOM and WebWorker types clash in one program, so `tsconfig.json` excludes `sw.ts`.
  - `pnpm typecheck` runs both configs.
  - `routes.ts` and `shell-cache.ts` use only `Request`, `Response`, `Cache` and `URL`, which both libraries have.
- **P9: E2E blocks service workers, except in `offline.spec.ts`.**
  - A worker that answers from its saved copy hides those requests from `page.route`. The connectivity and theme specs depend on `page.route`; the theme spec aborts `**/assets/*.js` to prove the theme script runs before the app.
  - So `playwright.config.ts` sets `serviceWorkers: "block"`, and `offline.spec.ts` sets `"allow"`.
  - With the block, no worker registers or controls the page on either browser. The prototype checked that directly.
- **P10: An offline E2E test refuses the household's socket too (`goOfflineLikeAPhone`).**
  - On WebKit, Playwright's `setOffline` closes open sockets but still lets a new one connect.
  - The app counts an open socket as online (M1.10), so after an offline reload "No connection" disappeared within about a second, in every one of 6 stressed runs.
  - A phone in airplane mode can't open a socket. Routing `/api/ws` to a socket that closes at once kept the banner on both browsers.
- **P11: The manifest.**
  - Name and short name "Baby tracker", the page's title.
  - `id`, `start_url` and `scope` are `/`, and `display` is `standalone`.
  - `background_color` and `theme_color` are `#fbfaf7`, M1.10's light background in sRGB.
  - Icons: 192 and 512 px as `any`, and the 512 again as `maskable`.
- **P12: The head tags.**
  - `theme-color` per scheme: `#fbfaf7` light and `#13100d` dark, M1.10's backgrounds. The M1.10 handoff asked for one per scheme, which only the page can give, since a manifest holds one.
  - `apple-touch-icon`, 180 px, which iOS puts on the home screen.
  - An SVG favicon.
  - The manifest link carries `crossorigin="use-credentials"`. A manifest is otherwise fetched without cookies, even from its own origin (MDN), and Access guards it like every other path (S4).
  - `apple-mobile-web-app-capable`, as in the spike that passed S1 to S4. The app then opens standalone even if a phone fetches the manifest without its cookie.
- **P13: The status bar stays iOS's default.** There is no `apple-mobile-web-app-status-bar-style`.
  - WebKit deprecated `black-translucent`, which draws white text even in light mode.
  - With the default style, iOS draws an opaque status bar above the page rather than over it. So the M1.10 handoff's "move the inset into the sticky wrapper" isn't needed, and the shell's safe-area padding stays.
  - No test here can see an iPhone's status bar, so M1.16 checks it on both phones in both themes.
- **P14: The icon is a cream crescent moon and a small dot on a muted violet tile**, from M1.10's calm, night-friendly palette.
  - Tile `#685f99` to `#483f72`; moon and dot `#faf1df`.
  - Full bleed, since iOS rounds the corners itself. The glyph sits well inside the maskable safe zone: at most 312 px from the centre, against the zone's 410.
  - One SVG is the source. `pnpm icons` renders the PNGs with Playwright's Chromium, and the PNGs are committed.
  - `scripts/icons.test.ts` checks each PNG's size against `ICON_FILES` and against the manifest.
- **P15: Sizes.**
  - The Worker bundle is unchanged at 253.04 KiB gzip.
  - The app's JS grows by 0.06 KB gzip.
  - `sw.js` is 1.88 KB (1.01 KB gzip) after the final review's install checks. It was 1.03 KB (0.60 KB gzip) before them.

## Review Focus

1. **A deploy while a phone has the app open or installed.** Expect the phone to save the new build and drop the old one once the new worker installs. An offline launch should open one whole build, never a new page with old assets. Tested in Task 2 (a changed asset or page gives a new version) and Task 1 (only other builds' caches are dropped). Since the final review, `service-worker-build-files.test.ts` also refuses a build whose files don't arrive as themselves. A rerun of the review's real-browser deploy race kept the previous copy, and the offline launch still opened.
2. **An expired Access session while online.** Expect opening the app to reach Access's sign-in, not the saved shell. Tested in Task 1 (Access's 302 passes through untouched) and Task 3 (Sign in is never answered from the saved copy). Since the final review, the E2E test "sends an expired session to Access's sign-in, not the saved app" also covers it, and it fails if the worker treats the redirect as offline or fetches the bare URL.
3. **Chromium's module scripts and stylesheets carrying `Origin`, with responses that vary on it (Vite's preview server).** Expect the saved JS and CSS to load offline anyway. Tested in Task 1 (`ignoreVary`) and Task 3 (the offline reload on Chromium).
4. **A phone that refuses the worker** (private browsing, blocked storage, signed out while registering). Expect the app to run as it does today, with no error. Tested in Task 3 (`unavailable`). Playwright's block resolves `register`, so no E2E test sees a refusal (a deferred minor).
5. **The first launch offline, before anything was saved.** Expect the browser's own offline page, not a blank or broken app. Tested in Task 1 ("fails as the network did when nothing is saved yet").

### Task 1: Who answers a request, and how the saved copy answers

**Files:**
- Create: `apps/web/src/service-worker/routes.ts`, `apps/web/src/service-worker/shell-cache.ts`
- Test: `apps/web/test/service-worker-routes.test.ts`, `apps/web/test/service-worker-shell-cache.test.ts`

**Interfaces:**
- Produces:
  - `type Route = "network" | "page" | "asset"`
  - `routeOf(request: Pick<Request, "method" | "mode" | "url">, origin: string): Route`
  - `SHELL_URL = "/"`
  - `cacheName(version: string): string`, which returns `bt-shell-<version>`
  - `staleCaches(names: readonly string[], current: string): string[]`
  - `pageResponse(request: Request, network: (request: Request) => Promise<Response>, saved: Pick<Cache, "match">): Promise<Response>`
  - `assetResponse(request, network, saved)`, with the same types

- [ ] **Step 1: Write the failing routing test.** Create `apps/web/test/service-worker-routes.test.ts`:

```ts
import { describe, expect, it } from "vitest"
import { type Route, routeOf } from "../src/service-worker/routes.ts"

const ORIGIN = "https://baby.example.test"

const request = (url: string, mode: RequestMode, method = "GET") => ({ url: new URL(url, ORIGIN).href, mode, method })

describe("routeOf", () => {
  it.each<[string, ReturnType<typeof request>, Route]>([
    ["opening the app", request("/", "navigate"), "page"],
    ["opening a tab's address with a query", request("/history?week=2026-W41", "navigate"), "page"],
    ["a path that only starts like the API", request("/apiary", "navigate"), "page"],
    ["a built script", request("/assets/index-CSxg7yjE.js", "cors"), "asset"],
    ["the manifest", request("/manifest.webmanifest", "no-cors"), "asset"],
    ["a household read", request("/api/me", "cors"), "network"],
    ["Sign in, a top-level navigation to the API", request("/api/login?return=%2F", "navigate"), "network"],
    ["a save", request("/api/diapers", "cors", "POST"), "network"],
    ["a HEAD of the app", request("/", "navigate", "HEAD"), "network"],
    ["Access's sign-in page", request("https://team.cloudflareaccess.com/cdn-cgi/access/login", "navigate"), "network"],
  ])("routes %s to %s", (_, routed, route) => {
    expect(routeOf(routed, ORIGIN)).toBe(route)
  })
})
```

```ts
type Network = (request: Request) => Promise<Response>

  try {
    return await network(request)
  } catch (failure) {
    const shell = await saved.match(SHELL_URL, SAME_FILE_FOR_EVERY_ORIGIN)
    if (shell === undefined) throw failure
    return shell
  }
```

```ts
import { createHash } from "node:crypto"
import { fileURLToPath } from "node:url"
import type { Plugin } from "vite"

const WORKER_ENTRY = "sw"
const WORKER_FILE = "sw.js"
const HTML_FILE = "index.html"

export interface Shell {
  readonly version: string
  readonly urls: readonly string[]
}

export const shellOf = (fileNames: readonly string[], html: string | Uint8Array): Shell => {
  const assets = fileNames.filter((name) => name.startsWith("assets/")).map((name) => `/${name}`)
  const urls = ["/", ...assets.toSorted()]
  const version = createHash("sha256").update(JSON.stringify(urls)).update(html).digest("hex").slice(0, 16)
  return { version, urls }
}

const sourcePath = (path: string) => fileURLToPath(new URL(path, import.meta.url))

export const serviceWorker = (): Plugin => ({
  name: "bt:service-worker",
  applyToEnvironment: (environment) => environment.name === "client",
  config: () => ({
    environments: {
      client: {
        build: {
          rolldownOptions: {
            input: { index: sourcePath(HTML_FILE), [WORKER_ENTRY]: sourcePath("src/service-worker/sw.ts") },
            output: {
              entryFileNames: (chunk) => (chunk.name === WORKER_ENTRY ? WORKER_FILE : "assets/[name]-[hash].js"),
            },
          },
        },
      },
    },
  }),
  generateBundle: {
    order: "post",
    handler(_options, bundle) {
      const worker = bundle[WORKER_FILE]
      const html = bundle[HTML_FILE]
      if (worker?.type !== "chunk" || html?.type !== "asset")
        this.error(`the build has no ${WORKER_FILE} or ${HTML_FILE}`)
      const shell = shellOf(Object.keys(bundle), html.source)
      worker.code = `const SHELL = ${JSON.stringify(shell)}\n${worker.code}`
    },
  },
})
```

```ts
declare const self: ServiceWorkerGlobalScope
declare const SHELL: { readonly version: string; readonly urls: readonly string[] }

const current = cacheName(SHELL.version)
const openSaved = () => caches.open(current)
const network = (request: Request) => fetch(request)

self.addEventListener("install", (event) => {
  event.waitUntil(
    openSaved()
      .then((saved) => saved.addAll(SHELL.urls.map((url) => new Request(url, { cache: "no-cache" }))))
      .then(() => self.skipWaiting()),
  )
})

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches
      .keys()
      .then((names) => Promise.all(staleCaches(names, current).map((name) => caches.delete(name))))
      .then(() => self.clients.claim()),
  )
})

self.addEventListener("fetch", (event) => {
  const route = routeOf(event.request, self.location.origin)
  if (route === "network") return
  const respond = route === "page" ? pageResponse : assetResponse
  event.respondWith(openSaved().then((saved) => respond(event.request, network, saved)))
})
```

## Handoffs (not M1.14 work)

- **Andrew, a decision (raised in the final review):** should a page wait for the network without limit?
  - On one bar or Wi-Fi with no internet behind it, iOS can hold a navigation for up to a minute on a white screen. That's no worse than without a worker, but the saved copy could answer instead.
  - **Option:** race the network against about 3 s. If the timer wins and a copy is saved, open it, and still fall back on a failed fetch as now (Workbox's `networkTimeoutSeconds`). Unit-test it with a network promise that never settles.
  - **Trade-off:** on a slow network with an expired session, the saved app opens and its first API call shows "Sign in to continue" instead of going straight to Access. Signing in is still one tap.
  - **Owner:** M5.4, unless Andrew wants it sooner.
- **M1.11, being built alongside:**
  - Both branches may edit neighbouring rows of the M1 table in `docs/implementation-plan.md`. Whichever merges second rebases.
  - From M1.14 on, E2E specs run with service workers blocked (P9). A spec that needs the saved copy sets `test.use({ serviceWorkers: "allow" })`, as `offline.spec.ts` does.
- **M1.12 (AC 11's full flow, P1):**
